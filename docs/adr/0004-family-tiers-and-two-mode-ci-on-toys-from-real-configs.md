# 4. Family tiers, and a two-mode CI built on toys from real configs

Status: Accepted

## Context

Supporting every architecture is not possible with hand-written kernels (ADR 1): each new piece costs kernels, tests
and CI time. The CI runs on the same Mac that is used for measurements, with a shared GPU, and the real models are
tens of GB that do not live on the machine.

## Decision

- **Tier 1** is a closed list of families: popular ones in daily use, or ones that bring pieces worth having, plus
  explicit requests. Each has one toy and one real model in the CI, fidelity against mlx-lm, and performance work.
  Only tier 1 may bring new pieces into the engine.
- **Tier 2** is any family built only from pieces tier 1 already exercises. It is registered, its fidelity is measured
  once, and it adds nothing to the CI; if a change breaks it, that does not block, and it is fixed if cheap or dropped.
- A piece that no tier-1 family uses is removed and becomes a named load error. Config keys the engine cannot run are
  load errors too, never a silent wrong load.
- **Toys:** 4 layers with random weights, generated by `lab-dev toymodels` from the real `config.json` kept in
  `ref/toy/real/`, with every deviation declared and checked (`toyMatchesReal`). One toy per tier-1 family.
- **Real models:** one per tier-1 family, the smallest that uses all its pieces; a piece the small one lacks is covered
  by the toy made from the larger model's config.
- **Two CI modes that never mix** (`scripts/ci.sh`): `--toy` on every integration (static checks, tests, the toys
  bit-exact against their goldens with the path checks and negative controls of ADR 2, and the toys' fidelity against
  mlx-lm fp32); `--real <models>` only with the named real models, when a change touches what only they cover or
  regenerates their golden.

## Alternatives considered

- Support whatever mlx-lm supports: unbounded kernel and CI work for families nobody uses here.
- Hand-made toy shapes: they drift from the real models and miss the pieces that matter.
- Real models on every integration: downloads and long GPU time on a shared machine.
- Graded levels mixing toys and real models: slower, and it blurred what each run actually proved.
- Toys with a tolerance against a CPU reference only: misses the bit-exact path bugs of ADR 2.

## Consequences

- A new family starts from its config and its toy; the real model comes last, for the golden and fidelity.
- Pieces disappear when their only users leave tier 1; loading such a model fails with the missing piece's name.
- The `--toy` mode has a time budget of a few minutes, which limits how many toys and steps it can carry.
- Toys do not have near ties nor exercise drafter copies or SSD experts: those need `--real`.
- Tier-2 families can break unnoticed; that is accepted.
